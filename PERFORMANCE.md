# h2lite — performance

Measured 2026-11-09 on Apple M2, 8 cores, Darwin 27.2.0 (arm64); Node v26.12.1; load generated by h2load nghttp2/1.70.0. Re-run with `node bench/showcase/matrix.js`.

## What this measures

Six HTTP servers answering the **same** request (a fixed header set and one of three response bodies) under the **same** offered load, driven by h2load. Each arm is a plain, honest responder — no tuning, no cache warmed by hand — so the number describes the stack, not a benchmark trick.

| Arm | Protocol | What it is |
|---|---|---|
| node:http | HTTP/1.1 | Node's HTTP/1.1 server |
| uWebSockets (http1) | HTTP/1.1 | The C++ HTTP/1 server often cited as the Node-ecosystem ceiling |
| node:http2 (stream) | h2c | Node's HTTP/2, the raw `Http2Stream` API |
| node:http2 (compat) | h2c | Node's HTTP/2, the `(req, res)` compatibility layer — **the drop-in baseline** |
| h2lite (stream) | h2c | This library, the `Http2Stream` API |
| h2lite (compat) | h2c | This library, the `(req, res)` API — what replaces `node:http2` in an app |

## How to read these numbers

- **μs/req is the metric that travels.** It is the server's own CPU time per request (measured inside the process), largely independent of the client and the machine. **req/s depends on load shape and host** and moves 8–13% run-to-run on *identical* code; it is shown for scale, not as the verdict.
- **The two HTTP/1.1 arms are not the same protocol.** HTTP/1.1 serialises one request per keep-alive connection; h2load is pointed at 512 connections to match the 512 in-flight requests the HTTP/2 arms carry over 32 connections. The per-request cost comparison is fair; the req/s ceiling is shaped by the protocol's connection model.
- **Ratios are against `node:http2 (compat)`** — the API you are replacing. Higher req/s is better; lower μs/req is better.

## Caveats, stated plainly

- Single machine, cleartext (h2c / HTTP/1.1 over loopback). TLS adds a shared record-layer cost to every arm and shifts absolute req/s; it does not change the per-request ranking.
- h2load's threads and the servers share cores. On this host the servers did not pin a core during a run (`busy%` in `out/showcase-raw.json`, averaged over a window that includes the server's idle tail, so the live figure is higher) -- therefore **req/s here is indicative, not the throughput ceiling**. `μs/req` is read directly inside the server and is the comparison to trust; raise `--threads`/`--duration` on a quiet machine to push req/s toward saturation.
- This is a header-bound GET microbenchmark. It says nothing about application work, streaming bodies over slow links, HPACK churn on unique headers, or back-pressure — those are measured by `bench/matrix.sh`, which is the paired proof harness.
- **Re-measure before quoting.** Numbers here are point-in-time on one host; per the project's own rule an unpaired before/after run cannot separate a change from noise.
